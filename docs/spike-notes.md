# Phase 0 Spike Notes

Run 2026-05-26 against a Linux NAS (Ubuntu 24.04 / kernel 6.8 / Docker 29.5) using the latest published Convex backend release `precompiled-2026-05-18-c3ac00a`.

This document captures the empirical evidence from Phase 0 tasks 1.1-1.8. It supersedes the original placeholder. **Several assumptions in `design.md` turned out to be wrong**; the corrections are recorded here and applied to the orchestrator code.

## What got confirmed vs. corrected

### Confirmed

- The standalone backend binary launches against a local SQLite file with no configuration and starts listening on `:3210` / `:3211` within seconds.
- Bogus admin keys are rejected with `BadAdminKey` HTTP 401. So our orchestrator's admin-key issuance is necessary, and there's no anonymous fallback.
- The `convex-backend` and `convex-dashboard` images on `ghcr.io/get-convex/*` are real and public; `:latest` is presently usable.
- Shared Postgres via `-d postgres-v5` plus a positional/env-supplied DB URL is the official path. The CLI listed both `postgres-v5` and `postgres-v5-multitenant` as options. We did not need `postgres-v5-multitenant` for our schema-per-instance model.
- The dashboard's "switcher" really does exist and is wired to a `listDeploymentsApiUrl`. The contract matches what we designed:
  ```
  GET <listDeploymentsApiUrl>
  → { "deployments": [{ "name": string, "adminKey": string, "url": string }, ...] }
  ```
  Source: `/app/src/components/DeploymentList.tsx` inside the official dashboard image.

### Corrected (these reshape the orchestrator code)

#### 1. There is NO `generate_key` binary in the release zip.

The release zip contains only `convex-local-backend`. The `generate_key` binary is not published as a standalone artifact, but the source is open (FSL-1.1-Apache-2.0, local build explicitly permitted) at `crates/keybroker/src/bin/generate_key.rs` — a 60-line clap wrapper around `KeyBroker::issue_admin_key`. So we **build it from the convex-backend git tag** in a multi-stage Dockerfile (`FROM rust:1` honors the repo's `rust-toolchain.toml` nightly pin automatically). 90s native compile on a desktop-class host, slower under qemu cross-compile. Functional equivalence to the image-shipped binary was verified on the NAS: a key generated by our from-source binary is accepted by the running backend with HTTP 200, a bogus key with 401. The image-pull dependency is gone entirely.

Output format of `generate_key spike-one <hex32-secret>`:

- stdout: `spike-one|01a06e47b4...` (single line, no trailing newline expected)
- stderr: `Admin key:\n` (decorative banner)

So `generateAdminKey()` must read stdout only and use the first line as the key. (Our current code already does this — only the binary path needed updating.)

#### 2. The backend is configured by ENV VARS, not by CLI flags, for almost everything.

The official `run_backend.sh` (entrypoint of the docker image) shows the real contract. Concretely:

| Concept           | Mechanism                                                                                 | Notes                                                    |
| ----------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Bind port         | `-p <port>` CLI flag                                                                      | default 3210                                             |
| Site-proxy bind   | `--site-proxy-port <port>` CLI                                                            | default 3211                                             |
| Bind interface    | `-i 127.0.0.1` CLI                                                                        | default `0.0.0.0`                                        |
| DB driver         | `-d postgres-v5` CLI                                                                      | also `mysql-v5`, `sqlite`, `*-multitenant`               |
| DB connection     | `POSTGRES_URL` env (or `MYSQL_URL`)                                                       | becomes positional `DB_SPEC` arg inside `run_backend.sh` |
| Origin (cloud)    | `CONVEX_CLOUD_ORIGIN` env                                                                 | NOT `CONVEX_CLOUD_URL`                                   |
| Origin (site)     | `CONVEX_SITE_ORIGIN` env                                                                  | NOT `CONVEX_SITE_URL`                                    |
| S3 endpoint       | `S3_ENDPOINT_URL` env                                                                     |                                                          |
| S3 buckets        | `S3_STORAGE_{EXPORTS,SNAPSHOT_IMPORTS,MODULES,FILES,SEARCH}_BUCKET` env                   | five env vars, full bucket names — NO flag prefix        |
| AWS creds/region  | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `AWS_S3_FORCE_PATH_STYLE` env |                                                          |
| S3 mode toggle    | `--s3-storage` CLI flag                                                                   |                                                          |
| Instance identity | `INSTANCE_NAME`, `INSTANCE_SECRET` env                                                    |                                                          |
| TLS-relaxed DB    | `DO_NOT_REQUIRE_SSL=true` env                                                             |                                                          |
| Disable telemetry | `DISABLE_BEACON=true` env                                                                 |                                                          |
| Rust log level    | `RUST_LOG=info` env                                                                       |                                                          |

The orchestrator code originally tried to pass S3 buckets and DB URL as CLI flags. Wrong. `src/server/supervisor/spawn.ts` has been rewritten to match the real contract.

#### 3. The dashboard switcher requires a port, not a URL, and must be reachable on `127.0.0.1` of the dashboard container.

The dashboard env var is `NEXT_PUBLIC_DEFAULT_LIST_DEPLOYMENTS_API_PORT` (a port number). The dashboard then constructs `http://127.0.0.1:<that-port>` and `fetch()`s the root path:

```ts
// from /app/src/components/DeploymentList.tsx in the dashboard image
const resp = await fetch(listDeploymentsApiUrl);
const data: { deployments: Deployment[] } = await resp.json();
```

Three consequences:

1. **The URL has no path.** The dashboard fetches `http://127.0.0.1:<port>/`, not `/api/deployments`. The orchestrator must serve the deployments JSON at the root path of whatever port it binds for this purpose.
2. **There is no auth header.** The dashboard does a plain `fetch()` with no Authorization. We must not require a bearer token on this listener. Mitigation: bind it to `127.0.0.1` only and rely on the dashboard sharing the orchestrator's network namespace.
3. **The host is hardcoded as `127.0.0.1`.** From the dashboard container's POV, the API must be on loopback. Easiest fix in our docker-compose: run the dashboard with `network_mode: service:orchestrator` so it shares the orchestrator container's loopback. Then `127.0.0.1:<port>` resolves to our orchestrator's listener.

The orchestrator now exposes the deployments listing on two surfaces:

- `GET /api/deployments` on the main HTTP port (auth-required, for humans/clients).
- `GET /` on a dedicated loopback port (default `8081`), unauthenticated, only for the dashboard. Configurable via `DEPLOYMENTS_API_PORT`.

#### 4. Default `--interface 0.0.0.0` is a foot-gun.

If we don't pass `-i 127.0.0.1`, the backend binds publicly on its port. Inside a container this is OK because the container's loopback is private to that container, but to keep the principle of least surprise we pass `-i 127.0.0.1` explicitly in `spawn.ts`.

### 5. Postgres single-tenant mode hardcodes the DB name to `carnitas`. Multi-tenancy on shared Postgres requires `-d postgres-v5-multitenant`.

This is the biggest finding of the spike and **invalidates the schema-per-instance design** in `design.md` §D3.

#### What I tried

Per the original design, `postgres-v5` driver + `CREATE SCHEMA convex_<name>` per instance + `search_path` connection option per instance.

#### What actually happened

- Passing `postgres://convex:pw@host:5432/convex` to the backend with `-d postgres-v5` fails with `cluster url already contains db name: /convex`. The single-tenant driver **forbids** a db name in the URL.
- Passing `postgres://convex:pw@host:5432` (no db name) with `-d postgres-v5` fails with `database "carnitas" does not exist`. The single-tenant driver **hardcodes** the database name to `carnitas`. There is no flag to override it.

Consequence: in `postgres-v5` mode, Convex expects to own a postgres database literally named `carnitas`. You cannot have two `carnitas` databases in the same postgres cluster, so you cannot run two single-tenant Convex backends against the same postgres cluster. Shared-postgres for many instances is fundamentally impossible in this mode.

#### What does work: `postgres-v5-multitenant`

Switching to `-d postgres-v5-multitenant`:

- The URL **must** include a db name (`postgres://user:pw@host:port/<db>`).
- `--instance-name`, `--instance-secret`, `--do-not-require-ssl` **must** be passed as CLI flags. Env-only is not enough in this mode (the binary rejects with `--instance-secret is required`).
- Both backends boot, listen on their loopback ports, and share the same postgres database. The `public` schema contains 5 system tables: `documents`, `indexes`, `leases`, `persistence_globals`, `read_only`.
- All rows in those tables carry an `instance_name` column. Verified empirically: after booting `spike-two` and `spike-three` in parallel against the same db, `SELECT DISTINCT instance_name FROM documents` returned both names, and the table held 238 rows total.
- Idle RSS per backend: ~75 MB, only slightly higher than the SQLite mode's 71 MB.

#### Implications for the orchestrator code

The whole "Postgres storage adapter" that creates/drops per-instance schemas is wrong-shaped. It now collapses to:

- `ensureSharedDatabase(name)` — `CREATE DATABASE convex` (or whatever db name we standardize on) if absent. That's it.
- There is no per-instance schema/db/CRUD. All tenants live in one DB.
- **Instance deletion is harder.** No `DROP SCHEMA CASCADE` equivalent. To purge a deleted instance's data we would have to issue `DELETE FROM <table> WHERE instance_name = $1` against the system tables — risky surgery on an undocumented internal schema. Our pragmatic stance: **on delete, we stop the process, drop Traefik routes, drop the SQLite orchestrator-side record, and free the ports — but we leave the rows in Postgres in place.** Operators who need true purge can drop the entire shared database and re-create it (destroys ALL instances). Real per-instance purge is a Phase 2 problem.

#### Risk: `postgres-v5-multitenant` may be unofficial

The official self-host docs only document `postgres-v5`. `postgres-v5-multitenant` is listed in the CLI help and works empirically, but it's not advertised. Convex may treat it as internal-to-Convex-Cloud and could change/remove it without warning. The orchestrator's whole value proposition (multiple tenants on one backend stack) hinges on this mode. **We accept this risk**, document it, and pin both image digest and (eventually) a backend version we've verified. Renovate updates the image; CI runs the integration test to catch regressions.

#### CLI invocation that actually works

The canonical incantation now baked into `src/server/supervisor/spawn.ts`:

```bash
convex-local-backend \
  "postgres://user:pw@host:5432/<shared_db>" \
  -d postgres-v5-multitenant \
  -p <cloud_port> \
  --site-proxy-port <site_port> \
  -i 127.0.0.1 \
  --s3-storage \
  --do-not-require-ssl \
  --instance-name <name> \
  --instance-secret <hex32>
```

Plus the S3 / origin / AWS env vars listed in §2 above.

### 6. The dashboard's "switcher" mechanism doesn't survive a remote deployment, and we don't need the dashboard container at all.

The official `convex-dashboard` container's switcher accepts only a single env var (`NEXT_PUBLIC_DEFAULT_LIST_DEPLOYMENTS_API_PORT`, NOT URL) and ALWAYS fetches `http://127.0.0.1:<that-port>/`. That URL resolves on the **user's browser's loopback**, not the dashboard server's, so it cannot work for any deployment where the user accesses the dashboard from a different host than the orchestrator. Verified on the NAS spike — user's browser → `127.0.0.1:18081` → ECONNREFUSED → falls back to the credentials login form.

The single-deployment env vars `NEXT_PUBLIC_DEPLOYMENT_URL` + `NEXT_PUBLIC_ADMIN_KEY` ARE picked up at build time in the static-export mode and would need a fresh build per instance — not viable for N instances on one container.

**Better path: ship the dashboard ourselves.** Convex publishes a `dashboard.zip` (~3 MB, 9.4 MB extracted, 191 static files) as a release asset on the same tag as the backend binary. We download and pin it in our Dockerfile, extract into `dist/dashboard/`, and serve it through the orchestrator's existing Hono process via host-header routing. Requests for `dashboard.<base>/*` → `dist/dashboard/*`. Requests for everything else → orchestrator UI/API.

To skip the manual credentials entry, the orchestrator UI embeds the dashboard in an `<iframe>` and uses the official **embedded-dashboard postMessage API** documented at `npm-packages/docs/docs/platform-apis/embedded-dashboard.mdx`. On mount the dashboard sends `{type: "dashboard-credentials-request"}` to `window.parent`. Our `DashboardEmbedPage` listens for that, replies with `{type: "dashboard-credentials", adminKey, deploymentUrl, deploymentName}`, and the dashboard auto-logs-in. Verified end-to-end on the NAS: clicking `Dashboard ↗` in the instance list opens an embedded dashboard view that lands directly on the Health page of the chosen instance, no form ever shown.

False starts before we found the postMessage API:

- `__NEXT_DATA__` JSON injection (setting `pageProps.deploymentUrl`/`adminKey` server-side): doesn't work. The dashboard reads sessionStorage at runtime, not pageProps.
- sessionStorage pre-fill via a `setup.html` handoff page: writes succeed, dashboard reads them, but the `isValidDeploymentInfo` state machine is only flipped by `onSubmit` (called from the form OR from `useEmbeddedDashboardCredentials`). A page reload with sessionStorage already populated falls back to the form.
- `?session=<token>` URL params with HTML rewriting: would have worked but is a homegrown protocol where postMessage is already the supported one.

Consequences:

- The `convex-dashboard` container in `docker-compose.yml` is gone (saved ~1.5 GB image pull).
- The `network_mode: service:orchestrator` hack is gone.
- The dashboard switcher concept is also gone — our orchestrator UI IS the switcher.
- Traefik routes both `orchestrator.<base>` and `dashboard.<base>` to the same `orchestrator` service via Docker labels.

## Code changes triggered by this spike

1. `docker/Dockerfile`: downloads `convex-local-backend` from the official GitHub release zip with per-arch sha256 verification, AND builds `generate_key` from the convex-backend source at the same git tag (no docker-image dependency). Both keyed off `ARG CONVEX_VERSION`, so they cannot drift.
2. `src/server/supervisor/spawn.ts`: switched to env-var configuration for DB, S3, origins, and instance identity. CLI args reduced to `-p`, `--site-proxy-port`, `-i 127.0.0.1`, `-d postgres-v5`, `--s3-storage`.
3. `src/server/storage/admin-key.ts`: default binary path changed from `/usr/local/bin/generate_key` to `/convex/generate_key`.
4. `src/server/config.ts`: `GENERATE_KEY_BINARY` and `CONVEX_BINARY` defaults updated to the new paths. Added `DEPLOYMENTS_API_PORT` (default `8081`).
5. `src/server/index.ts`: starts a second, loopback-only HTTP server on `DEPLOYMENTS_API_PORT` serving the deployments JSON at `/` without auth.
6. `docker/docker-compose.yml`: dashboard container removed entirely. Both `orchestrator.<base>` and `dashboard.<base>` routed via Traefik labels to the same orchestrator container (different host headers, same Hono backend).
7. `docker/Dockerfile`: new `convex-dashboard` stage downloads `dashboard.zip` from the same Convex release (sha256 pinned), extracts to `dist/dashboard/`.
8. `src/server/index.ts`: host-header middleware — requests with `Host: dashboard.*` are served from `dist/dashboard/`; everything else goes to the orchestrator UI/API.
9. `src/web/src/pages/DashboardEmbed.tsx`: new route `/instances/:name/dashboard` renders an iframe pointing at `https://dashboard.<base>/` and replies to the dashboard's `dashboard-credentials-request` postMessage with the instance's URL + admin key. Both `Dashboard ↗` buttons (list + detail) now link to that route.
10. `src/server/api/routes.ts`: `/api/instances` list now ships `adminKey` and `cloudUrl` per instance (it's an authenticated endpoint).
